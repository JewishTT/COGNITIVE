# God's Eye View Constitution

## Core Principles

### I. No Mocks — Only Real Functionality

Mock-код запрещён. Каждая функция должна работать с реальными данными и реальными API.

**Исключение:** Mock разрешён ТОЛЬКО по явному запросу пользователя.

- Не писать заглушки, заходы, заглушки-реализации
- Не использовать фейковые данные в продакшн-коде
- Каждый модуль тестируется на реальных фидах (ADS-B, AIS, TLE, USGS)
- Если API недоступен — код должен обрабатывать ошибку, а не возвращать мок

### II. Архитектурная Целостность

При интеграции кода из других проектов — переписывать под нашу архитектуру, а не копировать.

- Чужой код адаптируется под наши паттерны и модули
- Не импортировать "как есть" — рефакторить до интеграции
- Сохранять единый стиль: ES-модули, Vite, vanilla JS/CSS
- Каждый новый компонент встраивается в существующую структуру

### III. Оптимизированность — Наше Всё

Производительность — не после, а в процессе.

- Холодный старт <2с — это требование, не цель
- Интерполяция данных — плавная, без фризов
- WebGL/Three.js — рендерить только видимое
- Lazy loading для тяжёлых слоёв
- Профилировать перед оптимизацией, но оптимизировать всегда

## Performance Standards

- **Cold start**: <2s (median на M5/Chrome)
- **Frame rate**: 60fps на десктопе, 30fps минимум на мобильных
- **Memory**: не превышать 512MB на typical session
- **Network**: minimal polling, batch updates, WebSocket где возможно

## Code Quality

- **Zero dependencies** где возможно — vanilla JS
- **Tree-shaking** — не импортировать целые библиотеки
- **Type safety** — JSDoc или TypeScript для критичных путей
- **No console.log** в продакшн-коде
- **Error boundaries** — каждый слой обрабатывает свои ошибки

## Security

- API-ключи только в `.env`, никогда в коде
- `.env` в `.gitignore` — всегда
- HTTPS для всех внешних запросов
- CSP headers для XSS-защиты
- Нет eval(), нет innerHTML без санитайзации

## Development Workflow

1. **Сначала спроектировать** — перед кодом определить архитектуру модуля
2. **Профилировать** — измерить до оптимизации
3. **Оптимизировать** — сделать быстрее
4. **Протестировать** — убедиться, что работает
5. **Документировать** — если сложно объяснить, значит сложно использовать

## Governance

Конституция supérieur всем другим практикам. Изменения требуют документации и согласования.

Все PR/review должны проверять соответствие принципам.

Сложность должна быть оправдана. Если можно проще — делать проще.
